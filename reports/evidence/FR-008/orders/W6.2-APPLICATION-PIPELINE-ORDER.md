## Objective

Deliver the FR-008 Follow-Up Checkpoint G workflow: after an explicit Mark Applied action, the Founder can move a tracked job through the application pipeline and record terminal outcomes. Reuse `founder_triage_states` as current state and append an event for each real transition. Keep tracker lists paginated and include every active/terminal pipeline state in Applied/All Tracked. Preserve W6.1 behavior.

## State and transition contract

Use the existing states:

- Forward application stages: `applied`, `recruiter_screen`, `assessment`, `interviewing`, `final_interview`, `offer`, `accepted`.
- Terminal outcomes: `rejected_by_employer`, `withdrawn`, `no_response`.
- Existing Founder outcome `rejected_by_founder` remains distinct.

Rules:

- Add an explicit authenticated stage-update operation; do not infer a stage from opening a posting or external application link.
- `applied` is the start of this pipeline. Permit forward movement through the ordered stages, including skipping ahead when the Founder explicitly records it. Do not permit backwards movement.
- Permit a terminal outcome from `applied` or any non-terminal forward stage. Terminal outcomes and `accepted` cannot be reopened or changed in this slice; restore is a later work order.
- Repeating the current stage is an idempotent no-op. Each real state transition writes exactly one append-only activity event with action type, previous state, next state, and event time.
- Do not add a schema migration or a second current-state store. Stage changes must not create or reserve an outbound application action; only W6.1 explicit Mark Applied retains its founder-attested record.
- Preserve W6.1 canonical basic states, legacy `dismissed`/`snoozed`, API response compatibility, and the hosted adapter's explicit 501 boundary.
