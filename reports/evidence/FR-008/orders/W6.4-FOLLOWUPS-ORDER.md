## Objective

Deliver the W6.4 follow-up/reminder vertical slice from FR-008 §9.9 and §10.3. A Founder can set one or more dated follow-ups on a Saved or Applied job, edit the due date and optional private note, mark an item completed or reopen it, and see incomplete follow-ups grouped as due today, overdue, or upcoming.

Reuse `founder_follow_ups` and `founder_activity_events` from W4.1. Do not add or apply a migration. Persist each real follow-up mutation and its append-only activity event in one caller-owned transaction. A follow-up is a local tracker reminder; this increment does not send email or perform another outbound action.

## Contract

- Add authenticated API operations:
  - `GET /api/opportunities/{id}/follow-ups?page=1&page_size=50` — paginated follow-ups for the opportunity, including completed records.
  - `POST /api/opportunities/{id}/follow-ups` — create from required `due_date` (`YYYY-MM-DD`), optional `note_text`, and required `idempotency_key`.
  - `PATCH /api/opportunities/{id}/follow-ups/{follow_up_id}` — reschedule/edit `due_date` and/or `note_text`, or set `completed: true|false`; require an `idempotency_key`.
  - `GET /api/tracker/follow-ups?bucket=due_today|overdue|upcoming&page=1&page_size=25` — bounded, paginated incomplete follow-ups across eligible Saved and Applied jobs.
- Cap page sizes at 100. Normalize date-only values to UTC midnight in the existing `due_at` field and return `due_date` as `YYYY-MM-DD`. Define the three buckets using UTC calendar dates: incomplete records due before today are overdue, those due today are due today, and later dates are upcoming. Completed items are excluded from all three buckets.
- Follow-ups are allowed only while the canonical tracker state is `saved` or in the Applied bucket (`applied`, `recruiter_screen`, `assessment`, `interviewing`, `final_interview`, `offer`, `accepted`). Reject untracked, To Review, rejected, withdrawn, and no-response jobs.
- Allow multiple follow-ups for one opportunity. Keep completed records for history; deletion/archive is out of scope. A completed record can be reopened with `completed: false`.
- Trim optional note text, store blank as `null`, and reject text longer than 4,000 characters. Follow-up note text is returned only by the authenticated per-opportunity endpoint; do not include it in tracker summary rows, event metadata, feed projections, matching, ranking, prompts, or telemetry.
- Every real create, edit/reschedule, completion, or reopen writes exactly one event in the same transaction. Use `follow_up_created`, `follow_up_updated`, `follow_up_completed`, and `follow_up_reopened`; set event state fields to the current tracker state and put only `{ "follow_up_id": "…" }` in event metadata.
- Use the existing activity-event idempotency key for retries. A replay of the same operation returns its persisted follow-up without another event; reusing a key for another follow-up or action is a conflict. No-op edits and repeated completion state create no event.

## Founder UI and mock

- Show follow-up management in the opportunity detail drawer only for eligible Saved/Applied rows. Support create, reschedule, note edit, completion/reopen, and clear loading/empty/error states.
- Add a follow-up overview to Tracker with `Follow-up due today`, `Overdue`, and `Upcoming` categories, bounded loading and empty states, and links to the corresponding tracked job detail. Preserve existing Saved / Applied / Rejected / Closed / All Tracked behavior.
- Persist synthetic follow-ups and idempotency only in a dedicated local-storage namespace across refresh. Keep synthetic activity metadata ID-only. Do not seed notes or real Founder data.
- Add Chromium mock coverage for category placement, create/edit/complete/reopen, refresh persistence, and no duplicate event for no-op/idempotent actions.
