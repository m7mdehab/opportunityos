## Existing persistence and privacy boundary

W4.1 already defines `FounderFollowUpRecord` / `founder_follow_ups` with `opportunity_id`, `due_at`, `completed_at`, optional `note_text`, created/updated timestamps, and an opportunity/due/completed index. `FounderActivityEventRecord` already supplies a unique nullable `idempotency_key`; W4.1 also installs the append-only activity trigger and private-table RLS/browser-deny policies. No schema change is needed.

W6.2's tracker contract provides the canonical Saved and Applied state set and its bounded list conventions. No follow-up service, HTTP route, mock CRUD, or Founder UI exists yet. W6.3 established that record-plus-event operations should use a caller-owned transaction and that hosted writes stay unavailable until the adapter can persist atomically.

- `npx next typegen`, `npx tsc --noEmit`, `npm run lint`, Playwright, `python scripts/check_repository.py`, and Git diff checks are available.

## Decision and boundaries

Proceed with the pushed W6.4 order in an isolated feature worktree based on its docs-only integration checkpoint. Limit follow-ups to canonical `saved` and Applied-bucket states, preserve optional text as private per-opportunity data, and keep category summaries free of note content. Use existing W4.1 tables only. No email, provider, migration, live database, private profile/CV data, corpus, deployment, or Founder review is part of this increment.

No approved hosted atomic write or staging target is available. Keep Founder-testable at 0%; report this slice as partial and locally reviewable only, then continue into W6.5 without using Founder review as a blocking gate.
