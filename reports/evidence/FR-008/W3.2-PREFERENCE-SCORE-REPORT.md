# W3.2 — Explicit preference score

## Delivered

- Added assertion-only typed predicates for work mode, employment type, geography, relocation, compensation, industry, company, time-zone, and travel preferences. The existing `preference.track` and projected `career.target_role` signals are also included as preference dimensions.
- `preference.track` accepts only employment/independent track values. Other values on that predicate are ignored instead of being treated as a mismatch.
- A preference dimension is comparable only when it has a verified positive Founder assertion and explicit structured opportunity data. The scorer does not mine job description text for these values. Geography comparisons use structured country/region/city/remote-scope data, normalize country names to ISO-2, and allow a worldwide remote posting to match any stated geography preference.
- For the new categorical comparisons and typed compensation assertion, exact matches score 100 and direct mismatches score 20. Existing target-role-family and full-time/on-site premium dimensions retain their established raw scoring semantics. Missing, unsupported, or incomparable values remain unknown and are excluded. The overall `preference_score` is the equal-weight mean of comparable dimensions, rounded to two decimals, or `null` if none are comparable. This is an interim transparent baseline, not a calibrated set of weights.
- Typed minimum compensation preferences use amount, ISO currency, and interval together. Different or missing currencies/intervals remain unknown. Existing configured compensation signals and premium-shortfall tags remain compatible.
- `overall_fit_score` now aggregates only capability dimensions, normalized over active capability weights. Preference, objective geography eligibility, procurement budget/delivery compliance, and evidence-sufficiency dimensions do not enter that capability average. Preference-only unknowns do not increase the capability uncertainty penalty. Qualification remains a separate engine output.
- The score is stored in the existing evaluation-detail JSON and exposed as `scoring.preference_score` on opportunity detail. Historical detail payloads return `null`; no database migration or backfill was added.
