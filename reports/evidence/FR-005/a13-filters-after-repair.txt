Three of the four reasons are conditional -- they disappear the moment the founder's pack
declares the assertion. The fourth is unconditional and names the file responsible, because
no truth pack can make staleness work; only a worker that persists reverification results
can, and that is a future deliverable rather than something to paper over here.

Note `target_roles` is now seeded `label_only` rather than `rank_only`. Under substring
matching it demoted a fit-95 posting below a fit-30 one; it now uses token-set matching, and
until that predicate is proven against live data it labels rather than reorders.

--- Defect 1: a malformed param no longer takes the feed down ---

  PUT bad min_score ("abc")     -> HTTP 422
  feed still serves afterwards  -> HTTP 200, total=5
  filters still serve           -> HTTP 200
  PUT out-of-range min_score    -> HTTP 422
  PUT unknown param key         -> HTTP 422
  PUT unknown filter_id         -> HTTP 404

Before the repair the first of those returned 500 *after* persisting, and every subsequent
feed and filter request then returned 500 -- so the drawer could not load, and the founder
could not undo it from the UI at all. Recovery needed a raw HTTP client.

Both layers were required and both are present: validation rejects before the commit, and
each matcher degrades to no-match rather than raising, so a database that already holds a bad
value from some other path is still serviceable.
