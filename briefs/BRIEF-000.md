## 0. Read this first

This brief builds the substrate every later brief depends on. It ships no
product feature and touches no job source. Its job is to make the repository a
**self-maintaining source of truth** that three assistants across two vendors can
read without a human relaying anything between them.

You operate under the Master Plan's default contract (§13.0): one brief in, one
final report out. Resolve ordinary engineering decisions yourself. The Product
Constitution (§2) applies in full and nothing here overrides it.

---

## 1. Objective

A two-repository setup with four properties:

1. **Self-describing.** Any agent from any vendor, starting cold, reads one file
   and knows what this project is and what the rules are.
2. **Self-reporting.** Project state is generated from the repository, never
   hand-maintained, and cannot silently go stale.
3. **Readable by all three assistants** with no copy-paste relay.
4. **Private where it matters, public where it must be.** Code stays private.
   The documentation trail is mirrored publicly, and the mirror cannot publish
   anything that fails the content guard.

---

## 2. Why now

Master Plan §12.5 and §12.9 require the repository and its governance before any
phase runs autonomously, and §15.1 makes it Phase 0A. But the plan assumes a
single development agent. This project runs three assistants across two vendors,
none sharing memory, and the plan defines no state handoff, no canonical
instruction file, and no mechanism preventing state from rotting.

---

## 3. Founder prerequisites

Exactly one:

`gh auth login` completed on the founder's machine with `repo` and
`admin:public_key` scopes. The second scope lets you create the deploy key for
the mirror without the founder touching the GitHub UI.

Nothing else. No VPS, no domain, no LLM keys, no Truth Graph, no CV. If a step
appears to need any of those, it belongs to a later brief.

---

## 4. The two repositories

| | `opportunityos` | `opportunityos-docs` |
|---|---|---|
| Visibility | **private** | **public** |
| Contains | everything | mirrored subset only |
| Written by | Claude Code, via PR to `main` | the sync workflow, never by hand |
| Read by | Claude Code, ChatGPT | Claude chat, anyone |
| Authoritative | yes | no — derived artifact |

The public repository description should read as an engineering project: an
opportunity-acquisition platform for MENA. Its `README.md` is generated by the
sync workflow and states plainly that it is a read-only mirror, that the source
of truth is private, and that pull requests against it will not be accepted.

**The mirror is disposable.** It contains nothing that does not exist in the
private repository. If anything ever leaks into it, the remedy is to delete the
public repository entirely and re-run the sync. Write this in the mirror's
README so the option is obvious under pressure.

---

## 5. The content boundary

Two separate lines, and they are not the same line.

**Never in either repository:** secrets, keys, tokens, `.env` files, connection
strings, SSH keys.

**Never in the mirrored paths:** the founder's name, CV, résumé text, Truth
Graph, Capability Pack, personal email, phone number, application history,
tracker data, interview notes, salary figures, or any company shortlist tied to
him personally.

Personal data lives in the database and in `private/`, which is gitignored in
the private repository and never mirrored. `private/README.md` is the only
tracked file in there and explains what belongs in it.

Write all documentation in the master plan's own voice — "the founder", not a
name. The plan already reads this way throughout; keep it.

## 6. Scope — in

### 6.1 Repository creation

Create both repositories with `gh repo create`. Generate an ED25519 deploy key
with write access to the public repository, store the private half as the
`MIRROR_DEPLOY_KEY` secret in the private repository, and never write either
half into the working tree.

### 6.2 Private repository structure

A deliberate **subset** of Master Plan §39. Do not create empty framework
directories for code that does not exist yet.

├── briefs/

├── reports/

├── docs/

### 6.3 `.mirror-allowlist`

A plain-text file, one glob per line, defining exactly what the mirror
publishes. The sync copies nothing that is not matched here. Seed it with:

```text
docs/**
briefs/**
reports/**
AGENTS.md
```

Making this a config file rather than logic inside the workflow means the
allowlist can be widened later — mirroring `recon/` or `packages/schemas/`, for
instance — without touching CI. Do not widen it in this brief.

### 6.4 `AGENTS.md`

The canonical file, read natively by ChatGPT and Codex. Keep it under 150 lines;
it loads into every session and long files waste context. In this order:

1. One paragraph on what OpportunityOS is.
2. **"Read `docs/STATE.md` first."** The first instruction, not buried.
3. The hard rules, compressed from the Product Constitution: no fabricated
   claims about the founder, ever; coverage is not permission; no application,
   bid, or outbound message without explicit per-adapter authorization; no
   account creation; no credential use; secrets never committed; robots.txt and
   rate limits respected; no working around 403, 429, or CAPTCHA.
4. Repository topology — private source, public mirror, which is authoritative.
5. Where things live.
6. How to pick up work: STATE.md, then the active brief, then open ADRs.
7. How to finish: report to `reports/`, regenerate STATE.md, record consequential
   decisions as ADRs.
8. Pointers, not copies, to `docs/MASTER_PLAN.md` and
   `docs/PRODUCT_CONSTITUTION.md`.

### 6.5 `CLAUDE.md`

Claude Code does not read `AGENTS.md` natively. First line is the import
`@AGENTS.md`, followed only by Claude Code-specific notes that do not belong in
the vendor-neutral file. No duplication. Mention the `ln -s AGENTS.md CLAUDE.md`
alternative in `docs/INTEROP.md` but use the import, since a symlink loses the
ability to add Claude-specific notes.

### 6.6 `docs/STATE.md` — generated, never written

Hand-maintained state files rot. This one is a build artifact.

`scripts/generate_state.py` reads the repository and emits `docs/STATE.md`. No
arguments, no network, standard library plus `git` only. Every field derives
from repository facts:

| Field | Derived from |
|---|---|
| Generated timestamp | run time, UTC |
| Source HEAD | `git rev-parse --short HEAD` and commit subject |
| Active brief | highest-numbered brief with no matching report |
| Completed briefs | brief/report pairs with report dates |
| Last phase outcome | the pass/fail line of the most recent report |
| Open acceptance items | unchecked `- [ ]` boxes in the active brief |
| Open decisions | ADRs with status `proposed` |
| Accepted decisions | ADRs with status `accepted`, one line each |
| Blocked items | report sections headed "Blocked" or "Hard gate" |
| Source status counts | tallied from `SOURCE_REGISTRY.yaml` |
| Next prerequisites | the latest report's "next prerequisites" section |
| Mirror sync | source SHA and UTC time of the last successful sync |

Opens with a five-line summary an assistant can act on immediately: what this
is, what shipped last, what is active, what is blocked, what is next. Line one
is `<!-- GENERATED BY scripts/generate_state.py — DO NOT EDIT -->`.

The mirror-sync row is what lets a reader of the public mirror tell whether they
are looking at current state or a stale copy.

### 6.7 `docs/INTEROP.md`

Short, and honest about what each assistant can and cannot see:

- **Claude Code** — private repository, local working copy, full access. Reads
  `CLAUDE.md` → `AGENTS.md`.
- **ChatGPT / Codex** — private repository through its GitHub connector. Reads
  `AGENTS.md` natively. Full access.
- **Claude chat** — public mirror only, by `git clone`, read-only. **Sees
  documentation, briefs, and reports. Does not see code.**

State the consequence of that last line plainly. When Claude chat reviews a
phase report it can verify internal consistency, whether acceptance criteria
were actually addressed, whether the source registry matches the reported
evidence, whether STATE.md is current, and whether decisions that needed ADRs
got them. It cannot verify that the code does what the report claims. That is a
real gap in the maker/checker model of §13.6, and the mitigation is that Claude
Code's own checker agents and CI carry that burden, not the chat reviewer.

Then the tiebreak rule: **all three read `docs/STATE.md` before advising, and
none of them is authoritative over a committed ADR.** Where two assistants
disagree, the ADR log settles it. Where no ADR covers it, that is the signal to
write one.

### 6.8 Governance artifacts

- `docs/PRODUCT_CONSTITUTION.md` — Master Plan §2, verbatim.
- `docs/MASTER_PLAN.md` — the plan, unchanged.
- `briefs/TEMPLATE.md` — Appendix I structure.
- `reports/TEMPLATE.md` — §38 structure, including the mandatory "What this
  changes about the plan" section.
- `docs/adr/TEMPLATE.md` and `PDR-TEMPLATE.md` — per the Appendix I decision
  packet schema, with `status` of `proposed` / `accepted` / `superseded`.
- `docs/SOURCE_REGISTRY.yaml` — §32 schema, no entries. BRIEF-001 populates it.
- `docs/AGENT_PERMISSIONS.yaml` — §33 action classes, every external-write
  permission defaulting to `false`.

**`docs/adr/ADR-0001-repository-topology.md`** records the topology decision and
must state the actual reasoning, which is this: the private repository is the
default because there is no reason to publish working code, and the public
mirror exists for one specific reason — one of the two reviewing assistants,
Claude in the chat interface, has no GitHub credentials and no connector, and
therefore cannot read a private repository at all. The mirror is an
accessibility workaround for a tooling limitation, not a security measure. The
content guard is necessary hygiene for the mirrored subset, not the
justification for the topology. Record the rejected alternatives: fully public
(unnecessary code exposure), fully private (removes independent report review),
and a read-only access token pasted into chat (worse on both security and
manual effort).

### 6.9 Branch and CI policy

Branch-protect `main` on the private repository: no direct pushes, pull request
required, all three workflows passing. Document the parallel worktree policy
required by §12.9 in `AGENTS.md`: one branch per brief, one worktree per
parallel sub-agent, `main` always green.

The public mirror needs no branch protection. It is machine-written and
disposable.

## 7. The automation

Everything here exists so the founder does nothing and the repository stays
correct.

### 7.1 `state.yml` — on every push and pull request

**State freshness.** Run `generate_state.py`, diff against the committed
`docs/STATE.md`, fail with the diff printed if they differ. State is current or
the build is red. There is no third option.

**Report/brief pairing.** Fail if `reports/` gains a file with no correspondingly
numbered brief.

**Brief completion.** Fail if a report is added while its brief still has
unchecked acceptance boxes, unless the report contains a section headed
"Deferred acceptance items" naming each one.

**ADR integrity.** Fail on an ADR with no `status`, or a `superseded` ADR with no
successor reference.

### 7.2 `guard.yml` — on every push and pull request

**Secret scan, all paths.** Private keys, tokens, `.env` files, connection
strings, common API-key shapes.

**PII scan, mirrored paths only.** Everything matched by `.mirror-allowlist` gets
the strict ruleset from §5: emails, international phone patterns, the founder's
name, `.pdf`/`.docx` outside `docs/`. Patterns live in
`.github/pii-patterns.txt` so they can be tuned without editing the workflow.

Scoping the PII scan to mirrored paths is deliberate. Code and fixtures in the
private repository may legitimately contain an email-shaped test string; the
mirrored documentation may not.

### 7.3 `mirror.yml` — on merge to `main`

1. **Re-run the PII scan** against the exact file set about to be published.
   Failure aborts the sync and fails the workflow. This is the important one:
   a leak in a private repository is recoverable, a leak in a public mirror is
   not, so the guard runs again at the boundary rather than trusting that it
   passed earlier.
2. Copy every path matched by `.mirror-allowlist` into a clean checkout of the
   public repository. Delete anything in the mirror that no longer matches the
   allowlist, so removals propagate.
3. Regenerate the mirror's `README.md` stating that it is read-only, derived,
   and disposable.
4. Commit with the message `sync: <source-short-sha>` and push using
   `MIRROR_DEPLOY_KEY`.

A failed sync fails the workflow, which means a merge that did not reach the
mirror is visible rather than silent.

### 7.4 `check_mirror.py` — drift reconciliation, nightly and on demand

Fetches the public mirror, reads the source SHA from its most recent `sync:`
commit, and compares it against the private repository's `main`. If they differ,
re-run the sync and report. Scheduled nightly in `mirror.yml`.

This closes the one hole in §7.3: a sync can fail for reasons outside the merge
path — an expired key, a GitHub outage, a force-push to main. The nightly job
means the mirror is never more than a day stale without something saying so.

### 7.5 Failure messages

Every guard failure must name the rule that fired and how to fix it. A guard
that blocks without explaining trains people to disable it.

## 8. Scope — explicitly out

Their absence is a pass condition:

- Next.js, React, any front-end, any styling
- FastAPI, any server, any API of our own
- PostgreSQL, SQLite, any database, ORM, or migration
- Docker, Docker Compose, Caddy, any deployment
- Auth, users, sessions, tenancy
- Any job source adapter, any fetching of any source — that is BRIEF-001
- Truth Graph, CV parsing, document generation
- Any LLM API call
- Any agent framework or orchestration runtime
- Widening `.mirror-allowlist` beyond the four seed entries
- Empty placeholder directories for any of the above

---

## 9. Forbidden actions

- Creating any account beyond the two GitHub repositories
- Committing any secret, key, token, or `.env` to either repository
- Writing either half of the deploy key into the working tree
- Committing the founder's name, CV, or any personal identifier to a mirrored path
- Making the private repository public, or the mirror private
- Pushing to the mirror by any path that skips the §7.3 pre-push scan
- Any network request beyond GitHub and package registries
- Disabling, weakening, or adding exemptions to any guard

---

## 10. Hard gates — stop and report

- `gh` is not authenticated, or lacks `admin:public_key`
- Repository creation is refused
- A guard cannot be implemented without an exemption broad enough to defeat it
- The deploy key cannot be created without the founder using the GitHub UI

## 11. Constraints

- **Budget:** zero external spend. GitHub free tier only.
- **Time:** one session. If it overruns, commit what passes and report partial.
- **Concurrency:** `AGENTS.md`, the skeleton, and `.mirror-allowlist` are serial
  and first, since everything references them. Workflows, templates, governance
  artifacts, `generate_state.py`, and `check_mirror.py` are parallel-safe after.
  The mirror workflow is last, because it depends on the allowlist and the guard.
- **Council:** not required. Record ADR-0001 and proceed.

## 12. Acceptance criteria

**Structure**
- [ ] Private `opportunityos` exists with the §6.2 structure
- [ ] Public `opportunityos-docs` exists, is public, and contains only
      allowlisted paths
- [ ] No directory exists for a framework not yet in use

**Instruction files**
- [ ] `AGENTS.md` is under 150 lines and instructs the reader to open
      `docs/STATE.md` first
- [ ] `CLAUDE.md` line one is `@AGENTS.md` and does not duplicate it

**Generated state**
- [ ] `python3 scripts/generate_state.py` runs clean on a fresh clone with no
      third-party dependencies
- [ ] `docs/STATE.md` is committed, generated, carries the DO-NOT-EDIT marker,
      and includes the mirror-sync row
- [ ] Hand-editing `STATE.md` makes `state.yml` fail

**Guards — each verified by a deliberate failing case, then reverted**
- [ ] A report with no matching brief fails CI
- [ ] A fake API key in any path fails `guard.yml`
- [ ] An email address in a mirrored path fails `guard.yml`
- [ ] An email address in a non-mirrored path does **not** fail
- [ ] Every guard failure message names the rule and the remedy

**Mirror**
- [ ] A merge to `main` syncs the allowlisted paths to the public repository
      within one workflow run
- [ ] The mirror commit message carries the source short SHA
- [ ] Deleting a mirrored file and merging removes it from the mirror
- [ ] A PII violation in a mirrored path aborts the sync and nothing is pushed
- [ ] `check_mirror.py` detects an artificially reverted mirror and re-syncs
- [ ] The mirror's `README.md` states it is read-only, derived, and disposable
- [ ] `git grep -i` for the founder's name returns nothing in the mirror

**The real test**
- [ ] A fresh clone of the **public mirror**, plus `AGENTS.md` and `STATE.md`,
      is sufficient to understand the project with no other context

That last one is what the whole brief is for. Everything above it is a proxy.
