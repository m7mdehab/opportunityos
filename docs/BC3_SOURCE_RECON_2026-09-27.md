## Existing Greenhouse poll cost check

The official [Greenhouse Job Board API docs](https://docs.greenhouse.io/job-board.html) describe a lightweight job-list response by default, `content=true` for full descriptions, and a per-job GET endpoint. A read-only, governed preview of the existing `greenhouse:cloudflare` board using the current `content=true` request returned HTTP 200 with 393 jobs, 6,868,782 response bytes, and about 3.1 seconds transport time. Parsing that in-memory response through the current adapter took about 45.9 seconds; no persistence or evaluation was run. The parsed distribution was 11 core, 195 adjacent, 143 non-target, and 44 unknown roles.

For this checkpoint, Greenhouse adapter parsing now applies the canonical title-family classifier before expensive description extraction and skips only titles the classifier considers unambiguously non-target without description evidence. Adjacent families whose relevance depends on description evidence, and unknown titles needing review, are still fully parsed. Existing post-parse ATS admission still applies the full classifier before persistence/evaluation. The parser reports its prefilter count so poll diagnostics distinguish raw posts from parsed candidates. This is a bounded CPU reduction; it does not claim to solve all long poll runtimes, and no per-job detail fanout was introduced.

## Capacity and rollout boundary

The read-only live measurement on 2026-09-28 is `363,228,307` bytes (~346.4 MiB), only `3,773,293` bytes (~3.6 MiB) below the 350 MiB warning boundary. A read-only, registry-governed preview of the ten Himalayas target queries returned 200 responses, 20 jobs per query, and 1,269,347 response bytes total. This preview did not persist jobs. The targeted path is disabled by default; no source-write canary should run until capacity has safe headroom and the historical replay gate is accepted. Do not backfill or activate other sources in BC-3.

## Related implementation

- Himalayas implements the documented search route with Egypt and worldwide filters, target-role keywords, seniority/employment filters, recent ordering, and page-based pagination. `OPPORTUNITYOS_HIMALAYAS_TARGETED_SEARCH=true` enables the bounded multi-query path; it defaults off until an explicit write canary is safe. With the flag off, the worker uses the documented browse endpoint with `limit=20`.
- Broad Greenhouse/Lever batches use the canonical role-relevance classifier before persistence/evaluation. Only clearly non-target new postings are excluded; unknown roles remain reviewable. Historical rows are unchanged. Aggregate parsed/admitted/excluded counts are logged per source poll.
- Existing Lever/Greenhouse discovery continues to use governed watchlists/seeds and exact registry authorization. Newly reviewed sources remain inactive.
